# Формат контейнера NOX Vault (.nox), версия 1

Один и тот же формат используется для локального хранилища (`vault.nox` в приватном
каталоге приложения) и для экспортируемых резервных копий. У копии в заголовке
стоит `isBackup=true` и собственный парольный слот.

## Структура файла

| Смещение | Размер | Содержание |
|---|---|---|
| 0 | 4 байта | Magic `NOXV` |
| 4 | 1 байт | Версия формата = `1` |
| 5 | 4 байта | Длина заголовка, big-endian int (≤ 65536) |
| 9 | N байт | Заголовок: JSON в UTF-8 (см. ниже) |
| 9+N | до конца файла | Payload: AES-256-GCM шифртекст + тег подлинности 128 бит |

## Заголовок (JSON)

```json
{
  "formatVersion": 1,
  "createdAtEpochMs": 1735689600000,
  "isBackup": false,
  "passwordSlot": {
    "kdf": "argon2id",
    "saltB64": "<16 байт соли, Base64>",
    "memoryKb": 65536,
    "iterations": 3,
    "parallelism": 1,
    "wrapNonceB64": "<12 байт nonce обёртки ключа>",
    "wrappedDataKeyB64": "<DataKey, зашифрованный KEK из пароля>"
  },
  "recoveryWrapNonceB64": "<12 байт nonce или null>",
  "recoveryWrappedDataKeyB64": "<DataKey, зашифрованный ключом восстановления, или null>",
  "payloadNonceB64": "<12 байт nonce payload>"
}
```

Заголовок **не является секретным**: соли и nonce открыты by design, а DataKey
присутствует только в зашифрованном («обёрнутом») виде. Названия записей, теги,
заметки и все значения находятся только внутри зашифрованного payload.

## Криптографическая схема (envelope encryption)

1. `DataKey` — 32 случайных байта (SecureRandom), создаётся один раз при создании хранилища.
2. `KEK = Argon2id(мастер-пароль, соль; m=64 МиБ, t=3, p=1, выход 32 байта)` — Bouncy Castle.
   Поддерживается также чтение слотов `pbkdf2-sha256` (запасной вариант формата).
3. `wrappedDataKey = AES-256-GCM(KEK, свежий nonce, DataKey, AAD="NOX-v1/password-slot")`.
4. Слот восстановления: ключ восстановления — независимые 32 случайных байта
   (пользователю показывается один раз как 64 HEX-символа группами по 4).
   `recoveryWrapped = AES-256-GCM(RecoveryKey, свежий nonce, DataKey, AAD="NOX-v1/recovery-slot")`.
   Полная энтропия ключа делает KDF для этого слота ненужным.
5. Payload: `AES-256-GCM(DataKey, СВЕЖИЙ nonce при каждом сохранении, JSON-данные, AAD="NOX-v1/payload")`.
   Повторное использование nonce с одним ключом исключено конструкцией: nonce генерируется в `assemble()` на каждое сохранение.
6. Биометрия в файл контейнера **не пишется**: отдельная копия DataKey шифруется
   неэкспортируемым ключом Android Keystore и хранится рядом в `biometric.key`.
   Поэтому файл .nox переносим между устройствами.

## Payload (после расшифровки)

JSON объекта `VaultData` (kotlinx.serialization): `schemaVersion`, `items[]`, `folders[]`.
Запись: `id, type(категория), title, folderId, tags[], fields[{id,label,type,value,secret}],
attachments[{id,fileName,mimeType,sizeBytes,contentB64}], linkedIds[], favorite,
createdAt, updatedAt, lastOpenedAt, version`. Вложения v1 хранятся Base64 внутри
payload (лимит 2 МБ на файл), то есть тоже под AES-GCM всего контейнера.

## Проверка при открытии/импорте

1. Размер файла ≤ 64 МБ, magic, версия, длина заголовка — иначе понятная ошибка.
2. KDF по параметрам именно из заголовка (параметры можно повышать в будущем без ломки формата).
3. Расшифровка DataKey: провал тега GCM = «неверный пароль» (или повреждение слота).
4. Расшифровка payload: провал тега GCM после успешного шага 3 = «данные повреждены/изменены».
5. Частично расшифрованные данные наружу не отдаются никогда.
6. Если основной локальный файл не открылся, приложение пробует предыдущую хорошую
   версию `vault.nox.bak` (защита от прерванной записи) и при успехе восстанавливает её.

## Атомарное сохранение

`vault.tmp` (полная запись + fsync) → текущий `vault.nox` переименовывается в
`vault.nox.bak` → `vault.tmp` становится `vault.nox`. Временный файл — уже шифртекст,
открытых копий секретов на диске не существует ни в какой момент.
